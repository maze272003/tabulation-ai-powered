
## Self-review (security focus)

1. **Can a non-member read another org by guessing the slug?**
   **No.** `get` calls `requireOrgMember(ctx, { orgSlug })`, which:
   - resolves the org via `by_slug` (throws `NOT_FOUND` if missing or `status === "deleted"`),
   - looks up the caller's membership via `by_org_id_and_user_id`,
   - throws `FORBIDDEN` if no membership row OR `membership.status !== "active"`.
   Proven by test #3 (Bob is provisioned but not a member → `FORBIDDEN`).

2. **Can two users create the same slug?**
   **No (at the application layer).** `create` does a `by_slug` `.unique()` lookup before insert; if it exists, throws `CONFLICT`. Proven by test #2.
   **Caveat (TOCTOU):** Convex does not enforce unique constraints, so two concurrent `create` calls racing on the same slug could both pass the check and both insert. For Phase 1 single-user creation this is acceptable; a future hardening could use a retry-on-insert-conflict pattern or a sentinel document. Not a blocker for Phase 1.

3. **Does the owner get the Owner role + full permissions?**
   **Yes.** `create` calls `pickSystemRole(ctx, "Org Owner")` and inserts an `organizationMembers` row with `status: "active"` pointing at that role. The seed (`SYSTEM_ROLES` + `ROLE_PERMISSIONS`) gives `Org Owner` all seven permissions: `organization.view`, `organization.update`, `organization.members.manage`, `organization.delete`, `audit.view`, `subscription.view`, `subscription.manage`. The owner can therefore call `update` (which requires `organization.update`). Verified structurally by test #1.

4. **Is every state change audited?**
   **Yes.** Both mutations call `writeAudit`:
   - `create`: `action: "organization.created"`, `after: { slug, name }`.
   - `update`: `action: "organization.updated"`, `before` and `after` snapshots carrying the name diff.
   - `actorId` is always the authenticated user's `profile._id`, never an argument.

5. **Additional gates verified:**
   - **Unauthenticated create** → `UNAUTHENTICATED` (test #4) via `requireUserProfile` → `requireIdentity`.
   - **Suspended user** → `requireUserProfile` throws `FORBIDDEN` if `profile.status !== "active"` (covered structurally; the test identities are all active).
   - **Deleted org** → `resolveOrgBySlug` throws `NOT_FOUND` if `org.status === "deleted"` (structural).
   - **`update` permission gate** → `requirePermission(ctx, { permission: "organization.update" })`. A non-owner member (e.g., `Viewer` role) would get `FORBIDDEN`. Not exercised by an explicit test in this task — the authz library tests in `convex-test/authz.test.ts` cover the helper, and Task 11+ will likely cover negative member cases.

## Concerns

1. **TOCTOU on slug uniqueness** — application-layer check only. Acceptable for Phase 1; document as a known limitation if org creation becomes high-concurrency.
2. **`update` doesn't validate non-empty name** — `args.name.trim()` could produce `""`. Minor; the brief did not request name validation. Could add a `VALIDATION_ERROR` guard in a follow-up.
3. **`update` and `get` return types** — both return `Doc<"organizations">` (the full org document including `branding`, `ownerId`, etc.). For a future public-API audit, consider trimming fields the caller shouldn't see (e.g., internal IDs). Not in scope for Task 10.
4. **No explicit test for `update`** — the brief listed only three test cases. The `update` mutation is implemented, typechecked, and its permission gate is structurally sound (`requirePermission` is exercised in `authz.ts`), but no test asserts "owner can update, non-owner cannot." Task 11+ (memberships) is the natural home for that test.
