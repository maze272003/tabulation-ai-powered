## Expiry-test path taken

**Patched `expiresAt` directly via `t.run()`.** convex-test 0.0.55 has no
time-advance API: there is no `ts` argument on `mutation`/`query`, no
`asOf(timestamp)` builder. The only time-related surface
(`finishAllScheduledFunctions` / `finishAllScheduledFunctions(advanceTimers)`)
is designed for fake-timer interaction with the scheduler, not for advancing
`Date.now()` in a query/mutation body. `t.run(func)` exposes the mock
mutation context, so the test patches the invitation row's `expiresAt` to
`Date.now() - 1000` before calling `accept`. This is deterministic and
asserts the real code path (the `Date.now() > inv.expiresAt` branch).

## Pre-existing bug fixed in `entitlements.ts`

`requireLimit` was looking up `plan.limits[resource]` where `resource` is
the short usage name (`"members"`). But plan limits are keyed with a `max`
prefix (`"maxMembers"`, `"maxEvents"`, etc.) per `schema.ts` and
`constants.ts`. The lookup returned `undefined`, so `hasLimit` returned
`false`, and **every** call to `requireLimit` would throw
`LIMIT_EXCEEDED` — even with usage = 1 and a ceiling of 5.

This bug had been latent because no prior task actually invoked
`requireLimit` against real plan data (the existing `entitlements.test.ts`
exercises `hasLimit` directly with already-correct keys like `"maxMembers"`).

**Fix:** added `limitKeyForResource(resource)` which maps `"members"` →
`"maxMembers"` (capitalize first letter, prefix with `max`). `requireLimit`
now resolves the limit key explicitly and throws `LIMIT_EXCEEDED` only when
`current >= max` (or when the limit is missing/non-numeric). The pure
`hasLimit` helper is unchanged.

## Design deviation: side-effect on expired accept

The brief's `accept` did:

```ts
if (Date.now() > inv.expiresAt) {
  await ctx.db.patch(inv._id, { status: "expired" });
  throw appError(ErrorCode.CONFLICT, "Invitation has expired");
}
```

This doesn't work as written: Convex mutations are atomic, and a throw
rolls back **all** writes performed by the mutation (including the
preceding patch). The side-effect would silently vanish.

Options considered:

1. **Drop the side-effect, keep the throw** (chosen). The invitation stays
   `"pending"` with a stale `expiresAt`; subsequent accept attempts
   re-evaluate the same check and re-throw `CONFLICT`. Functionally safe
   but the row's `status` doesn't reflect reality.
2. Run the patch in a separate scheduled function (`runAfter(0, ...)`) so
   it commits independently of the throwing mutation. Workable but adds
   machinery for marginal benefit.
3. Sweep pending-but-stale invitations to `"expired"` in a Phase 2 cron.

I chose (1) and added a code comment flagging the tradeoff and pointing at
(3) as the Phase 2 follow-up. The test asserts that re-accepting still
fails, which is the actual safety property.

## Concerns

1. **Pending invitations do not reserve quota.** `requireLimit` is checked
   at `create` time but `usage.members` is only incremented at `accept`
   time. An org on the Free plan (`maxMembers = 5`) can mint an unbounded
   number of pending invitations. They only fail at accept time once the
   membership ceiling is reached. This is per the brief; flagging it as a
   follow-up consideration (e.g. count `status="pending"` rows against the
   limit, or increment a separate `invitations` usage counter on `create`).

2. **`accept` does not write a `before` snapshot of the membership it
   creates/updates.** The audit entry records the invitation's
   `pending → accepted` transition, but not the membership write itself.
   This matches the brief; if the team wants dual audits (one for the
   invitation, one for the membership upsert), that's a small follow-up.

3. **`members.list` returns all memberships including inactive ones.** A
   future UI may want to filter to `status === "active"` by default. The
   schema already supports this; the query just isn't filtering.

4. **`.filter()` after `.withIndex()` in `listForUser`/`listForOrg`/
   `create`.** Lint warns about this pattern (`@convex-dev/no-filter-in-
   query`). It matches the existing convention in `organizations.ts` /
   `seed.ts`. The filters are on `status` literals that can't be folded
   into the existing indexes without adding new ones; the row counts per
   org are bounded by `maxMembers`, so it's not a scale concern.

## Fix

Follow-up commit addressing four review findings on the Task 11 build
(branch `phase1-foundation`). All four were real correctness/entitlement
bugs in Phase 1's core.

**Commit:** `a3da9ce` — `fix: enforce requireLimit on accept, guard usage
decrement, unify entitlements, normalize email`

### Finding 1 — `invitations.accept` skipped `requireLimit` (quota bypass)

`accept` inserted a membership and bumped `usage.members` without ever
checking the limit, so on Free (`maxMembers=5`) an admin could mint N
invitations and have all of them accept past the ceiling.

**Fix:** `convex/invitations.ts:154-157` — after resolving the existing
membership, gate a `requireLimit` call on whether this acceptance actually
increases the active count:

```ts
const increasesActiveCount = !existing || existing.status !== "active";
if (increasesActiveCount) {
  await requireLimit(ctx, await getSubscription(ctx, inv.orgId), "members");
}
```

If the invitee is re-activating an already-active membership, no check
runs (no increment happens). If they are inserting a new row OR flipping
inactive→active, `requireLimit` runs first and throws `LIMIT_EXCEEDED`
before any write — Convex rolls back, so no partial state.

**Covering test:** `convex-test/members.test.ts` — "closes the accept-time
quota bypass: 5th accept hits LIMIT_EXCEEDED (Finding 1)". Alice owns
the org (slot 1); Bob/Carol/Dave/Eve accept to fill to 5; Frank's 5th
accept throws `LIMIT_EXCEEDED` and he does not appear in `members.list`.
Test count goes 24 → 25.

### Finding 2 — `members.remove` double-decremented usage

`remove` decremented `usage.members` unconditionally. Calling it twice on
an already-inactive membership drove the counter negative (clamped to 0
by `Math.max` in `incrementUsage`), creating phantom quota headroom the
next time someone accepted an invitation.

**Fix:** `convex/members.ts:95-97` — only decrement on the
active→inactive transition:

```ts
if (target.status === "active") {
  await incrementUsage(ctx, actx.org._id, "members", -1);
}
await ctx.db.patch(args.membershipId, { status: "inactive" });
```

Re-removing an inactive member is now a no-op for usage. The audit's
`before` snapshot still records the real prior status.

### Finding 3 — `requireLimit`/`hasLimit` semantic divergence

`requireLimit` inlined its own limit check (with a `limitKeyForResource`
map) while `hasLimit` still took a raw limit key. Both had a parameter
named `resource` meaning different things — a caller writing
`hasLimit(plan, "members", x)` got silent `false` forever, and any future
drift between the two paths would reintroduce Finding 1-class bugs.

**Fix:** `convex/lib/entitlements.ts:50-65` — `requireLimit` now resolves
the limit key and routes through `hasLimit`, making it the single code
path:

```ts
const limitKey = limitKeyForResource(resource);
if (!hasLimit(plan, limitKey, current)) {
  throw appError(ErrorCode.LIMIT_EXCEEDED, `Limit reached: ${resource}`, {
    resource, current, max: plan.limits[limitKey as keyof typeof plan.limits],
  });
}
```

`limitKeyForResource` and `hasLimit` are unchanged. The Task 9 pure
test `entitlements.test.ts` (calls `hasLimit(plan, "maxMembers", 4)`)
still passes — signature untouched.

### Finding 4 — email case-fragility in `accept`

`accept` compared `inv.email !== profile.email` exactly. Invitation email
is lowercased at `create`, but `profile.email` may arrive mixed-case
from the auth provider — a legitimate invitee got `FORBIDDEN`.

**Fix:** `convex/invitations.ts:136` — normalize before comparing:

```ts
if (inv.email !== profile.email.toLowerCase()) {
  throw appError(ErrorCode.FORBIDDEN, "Invitation is not for you");
}
```
